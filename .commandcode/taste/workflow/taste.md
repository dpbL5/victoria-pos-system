# workflow
- Keep the sub-agent/skill roster lean and project-specific: prune agents and skills that are rarely used for the current project rather than retaining a large generic set (e.g., after learning there were 60 sub-agents, user asked to remove ones rarely used for this project). Confidence: 0.65
- Keep documentation files (CLAUDE.md, AGENTS.md) in sync with structural code changes such as route consolidation, feature moves, or navigation updates. Confidence: 0.80
- For one-off data migrations (schema restructures), write a separate idempotent script wired as its own npm script (e.g., `migrate:walkin-customer-name`), executed after the DDL is applied, that runs inside transactions, copies values to the new field before detaching old references, and only deletes rows verified to have no remaining references (counting sessions/invoices/memberships first) — rather than raw inline SQL or throwaway code. Confidence: 0.70
- Prefers implementation work to be broken into explicit phases for easier rollout ("Chia ra các phase để dễ triển khai"): phases ordered by dependency and risk (quick cleanup first, then shared foundations, enforcement, adoption, legacy cleanup last), each independently shippable with its own verification step, with parallelizable phases called out explicitly. Confidence: 0.80
- Before implementing complex multi-file features, enter plan mode, explore existing code thoroughly, and write a structured implementation plan document covering all phases — including both business/payment logic calculation and UI design — before starting. Confidence: 0.85
- When a user mentions multiple distinct features or changes, treat them as separate implementation tasks rather than bundling them into one plan. Confidence: 0.65
- Use `todo_write` to track phased, structured progress through complex features, updating individual task statuses as work progresses. Confidence: 0.75
- When a series of `edit_file` calls corrupts a file, read the full file and rewrite it entirely from scratch rather than attempting to fix broken incremental edits. Confidence: 0.80
- Organize tests by module/feature in `__tests__` directories, testing pure functions and Zod schemas with Vitest (`describe`/`it`/`expect` + `safeParse`). Confidence: 0.85
- Verify changes in this order: typecheck (`tsc --noEmit`) and ESLint in a single combined step, then run tests (`vitest run`), then production build (`next build`). Confidence: 0.76
- Commit changes as small, feature-grouped commits (prefixed with type like `feat`/`fix`/`chore`/`refactor`) rather than one large commit, each with a descriptive Vietnamese message and `Co-authored-by: CommandCodeBot` trailer — the user explicitly restated this preference and its rationale: "I prefer commits many changes for easy to control diff" (e.g., session work was split into separate UI / backend / test commits). Confidence: 0.97
- The user expects the working tree to end fully committed, with nothing left behind: when asked whether to also commit leftover pre-session changes they replied "Có", and when the agent left debug/scratch files out (`resp.json`, `sessions.html`, `cookies.txt`, `.commandcode/taste/*`) the user followed up with a terse "commit th rest" — so ALL remaining files (code and non-code alike, including debug artifacts and taste files) get reviewed via `git diff`, grouped into topic-based `chore` commits, and committed; the agent may still flag credential-bearing files (e.g., `cookies.txt` containing a login session) for `.gitignore`, but should not refuse to commit them when asked. Confidence: 0.8
- When suggesting commit groups, merge any groups that touch the same file into a single commit rather than splitting them into separate commits that share a file. Confidence: 0.90
- After merging a feature/dev branch into `master` or `main`, delete the merged branch both locally (`git branch -d`) and remotely (`git push origin --delete`). Confidence: 0.90
- Parallelize independent exploration reads (e.g., reading schema.prisma + glob-ing barrel `index.ts` files + reading domain directories) in a single tool-use block to quickly map project structure before diving deeper. Confidence: 0.75
- When merging dev into master/main, use `--no-ff` to preserve branch history and create an explicit merge commit. Confidence: 0.80
- When a commit accidentally includes unrelated files (e.g., auto-generated config), use `git reset --soft HEAD~1` + `git restore --staged <unrelated>` to fix the commit scope without losing work. Confidence: 0.75
- Prefers finding and installing well-vetted community skills (skills.sh leaderboard, `npx skills` CLI) over building custom tooling from scratch; vet candidates by install counts, GitHub stars, and security audits, and present the trade-offs before installing. Confidence: 0.65
- Run CLI installers/commands in non-interactive mode (e.g., `-y`) so they don't hang on interactive prompts during agent runs; if a command hangs, retry it with the non-interactive flag. Confidence: 0.70
- When a review yields multiple prioritized candidates, user prefers to work through the batch in one session (e.g., "Let do first 6 candidates") via a structured "grilling" decision-tree process: verify facts first, then ask round-based questions covering the whole decision frontier — each with concrete options and a clear recommendation — and wait for answers before unlocking dependent questions; the user tends to accept the recommended option wholesale rather than weighing each choice: in Round 1 they answered "Q1c the rest is a" (5 of 6 recommendations), and in Round 3 explicitly said "tôi chọn tất cả theo bạn khuyến nghị" (all 6) — effectively delegating the design decisions to the agent. Confidence: 0.80
- When facing architectural design decisions that affect user-visible behavior (e.g., pricing flow, delete scope, pause behavior), present structured `ask_user_question` prompts with concrete options each carrying a `(Recommended)` label and a description explaining the trade-off; the user often accepts the recommended option rather than weighing alternatives (e.g., chose the recommended "Tối ưu DB + giảm request" option over the bigger bootstrap-endpoint refactor and the connection-string change when optimizing /sessions). But this is NOT absolute: when the recommended option doesn't match how the business actually runs, the user overrides it — in the multi-pricing-group checkout fix they twice chose the non-recommended options ("Thu hết 1 lần" over "thu từng nhóm riêng", and "Chọn tay từng người" over "theo thứ tự"), so the agent should keep recommendations genuinely optional and be ready to implement the user's own choice. Confidence: 0.6
- When surveying code before designing a complex feature, dispatch multiple `explore` sub-agents in parallel (e.g., one for schema/relations, another for UI/API endpoints) to maximize exploration throughput rather than feeding them sequentially; this is a specific instance of the general parallelization principle applied to sub-agent exploration. Confidence: 0.55
- When refactoring a module, prefers to do the complete job in a single change — extraction plus deduplication of duplicated code paths plus test coverage together — over a minimal behavior-preserving extraction with cleanup and tests deferred to later steps (chose "extract + dedup + tests in the same PR" over the recommended minimal option). Within that single change, prefers a strict sequence of separate commits — extraction first, then deduplication, then tests last — rather than writing tests before the dedup step as a safety net (chose "trích → dọn → test, từng bước commit riêng" over the recommended test-first approach). Confidence: 0.65
- When ordering a batch of refactoring candidates, prefers risk-first sequencing: tackle the riskiest/highest-value candidates (e.g., core check-in/check-out transaction logic) before trivial cleanups (e.g., deleting migration shims) — deliberately overrode the agent's recommended trivial-first "quick wins" order (chose "b: rủi ro trước → trivial sau" over recommended "a: trivial trước → rủi ro sau", planning C1→C2→C3→C5→C6→C4). This applies even though the user otherwise delegates design decisions to the agent's recommendations. Confidence: 0.7
- When building a new shared/reusable component, prefers creating a dedicated demo/testing page or tab first to visually preview the component in isolation with real data before integrating it into production pages. Confidence: 0.70
- Prefers using specialized sub-agents (e.g., `UI_Finish-Gate_Reviewer`, QA agents) for quality-gate tasks — UX auditing, code review, and re-reviewing core business logic for logic holes — rather than performing audits manually; the user explicitly requests these agent reviews, including repeat passes over critical flows (e.g., "Đánh giá lại use-case check-in và check-out bằng agent QA một lần nữa xem có lỗ hổng hay lỗi logic nào không. Nhất là tính toán giờ chơi"), with special attention to money/time calculations (play-time math, pricing, preview-vs-checkout consistency). Confidence: 0.85
- Before finalizing a data migration/cleanup script, first survey the actual DB state with a temporary throwaway script (count/list candidate records and their relations) rather than relying on assumptions about data shapes (e.g., a `Khách #…` name pattern) — real data can differ from expectations and cleanup criteria must be adjusted to match reality; after running the migration, re-verify the resulting DB state (e.g., zero remaining candidates, no sessions left without a name) and delete the temporary scripts afterwards. Confidence: 0.70
- tsx runs in CJS mode in this project, so DB/script files must wrap their logic in an async `main()` with `.catch(...)`/`.finally(prisma.$disconnect)` instead of top-level await; prefer temporary script files (prefixed `_`) over inline `tsx -e` one-liners to avoid shell-escaping issues — and place them inside the project (e.g., `scripts/`), because the agent scratchpad lives outside the project and cannot resolve `@/` path aliases — then remove those temporary files after use. Confidence: 0.75
- When relocating a feature's logic to another stage of the flow (e.g., moving pricing selection from check-in to checkout), preserve existing capabilities (e.g., splitting a group across multiple pricing tables) rather than dropping them for simplicity — user chose to keep group splitting over the recommended single-price-table simplification. Confidence: 0.55
- When lint/typecheck surfaces warnings, first determine via `git diff` whether each warning is pre-existing or introduced by the current change; fix only the ones the change introduced and leave pre-existing warnings untouched to avoid scope creep (agent explicitly checked `git diff` on `today-shift-screen.tsx` to prove `Clock`/`Minus`/`Package` warnings predated the change, removed only its own leftover `CheckoutResponse` interface, and re-ran eslint excluding the pre-existing-noise file). Confidence: 0.6
- Design refinement uses a "strip" philosophy: diagnose the primary job of the interface (e.g., "collect payment"), then remove obstacles to that job — visual monotony, excessive nesting, overloaded CTAs, missing affordances — without gutting capability. Each fix is scoped to a single identified issue and tracked via todo_write. Confidence: 0.65
- After picking one option from a multi-choice architectural decision, the user may follow up by asking about the alternatives they didn't pick (e.g., chosen "bỏ Payment" then asked "nếu bỏ MembershipPayment thì sao?") — they want a full pro/con breakdown of the other direction before committing; the agent should treat the initial choice as provisional and be ready to analyze tradeoffs of the unchosen paths without treating it as indecisiveness. Confidence: 0.6
- After a QA/review report classifies findings by severity (critical/major/minor), the user follows up with a terse directive to fix the top tier immediately in one batch (e.g., "Sửa luôn các lỗi Major" after the QA report listed 4 Major + 8 Minor) — implement ALL findings of that tier without per-item confirmation, track each via todo_write, and verify with typecheck + the full test suite + lint before summarizing; lower tiers stay deferred unless explicitly requested (here the user picked only the Majors, not the agent's broader recommendation to also fix cheap minors). Confidence: 0.6
- When the user says "continue" after a design review + refinement pass, proceed autonomously to the next recommended design mode (as listed in the review report's recommendations) without pausing for confirmation — the user expects the agent to self-direct through the full review-to-fix pipeline. Confidence: 0.7
- Design reviews follow a structured report format: header with target/score/date, TL;DR verdict, 5 named heuristic scores (First impression, Hierarchy, Color voice, Type voice, Interaction feel — each out of 10), cognitive load assessment rated High/Medium/Low with PASS/WATCH/FAIL items, "What's Working" section, priority issues (P0–P6 by functional severity: P0=functional blocker, P1=cognitive overload, P2+=hierarchy/clutter/brand), smell detection (template tells), and ordered recommendations each mapped to a design mode (/interaction, /relayout, /recolor, /refine). Confidence: 0.7
- Design review reports are saved as both `.md` and `.html` in `.commandcode/design/`. The HTML version uses a dark theme with monospace `// SECTION` headers, corner-box accent decorations, and a color-coded priority issue list (rose for P0-P2, amber for functional, purple for brand). Confidence: 0.65
- When a major refactoring decision requires a DB migration (schema change + data backfill), the user expects a structured sequence: (1) backup/old-data dump first, (2) Prisma schema edit + `db push --accept-data-loss`, (3) backfill from backup via script, (4) code changes, (5) verify tsc + vitest. The backfill script should use `@/generated/prisma` with the PrismaPg adapter pattern (not raw psql, not raw pg), read old data from a JSON backup file (since the Prisma client no longer has the dropped model), and be idempotent. Confidence: 0.7
- The user expects full pro/con comparison tables (with a summary row showing: code changes needed, backfill complexity, migration risk, long-term cleanliness) when presented with two architectural options, even when they've already tentatively chosen one — they may reverse their choice after seeing the full tradeoff analysis (initially chose "bỏ Payment" then reversed to STI after seeing the comparison). Confidence: 0.7
