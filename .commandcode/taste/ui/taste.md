When a component is reported broken this way, apply a comprehensive responsive fix across the whole component ("sửa lại UI responsive tổng thể") rather than patching a single element; keep the desktop layout unchanged with buttons still horizontal to the right. Confidence: 0.8
- Prefer letting long text content wrap to multiple lines (`break-words`, `flex-wrap`) to display fully rather than truncating with `truncate`, even in constrained flex containers; truncation was tried for long employee names but the user explicitly asked to instead wrap/xuống dòng so information is shown in full. Confidence: 0.60

Confidence: 0.75

- For responsive data views that swap between table (desktop) and card-list (mobile), render both components simultaneously in the DOM and toggle visibility via CSS breakpoints (`md:hidden` / `hidden md:block`) rather than using JS-based `matchMedia`/`useMediaQuery` hooks. - Keep dialogs single-purpose: when a dialog would need to embed a business flow that has its own dedicated screen (e.g., member creation/renewal embedded in the check-in dialog), remove the embedded flow and instead show an explanatory warning plus a button that closes the dialog and routes (`router.push`) to the dedicated tab. The user explicitly requested this ("nhấn tạo hội viên -> chuyển sang tab đăng ký hội viên") and had the embedded "Gia hạn & check-in" flow removed entirely rather than kept with guard fixes. The same single-purpose preference extends to operationally distinct tasks bundled into one dialog: the user asked to split tool counting out of the open-shift dialog ("Tôi muốn tách hai việc mở ca và đếm dụng cụ") — opening a shift keeps only cash + notes, and a separate "Đếm dụng cụ" button + dialog is added while close-shift counting stays as-is. Confidence: 0.85

- Numeric quantity inputs should support direct keyboard entry, not only +/- stepper buttons: render an `Input` backed by a raw string state (so it can be typed/cleared) and clamp to min/max on submit — user explicitly requested keyboard entry for the walk-in player count ("Số người chơi nên cho phép thêm nhập số lượng bằng bàn phím"), with the stepper kept as a complement. Use `type="text"` + `inputMode="numeric"` + `pattern="[0-9]*"` + regex validation (and `maxLength`) rather than `type="number"`: React number inputs emit transient intermediate values ("1.", "01") that desync the DOM from state and make the + button jump by 2 (user reported "ấn + thì giá trị bị +2" in the player-count field). Stepper buttons must use functional updates (`setState(current => ...)`) so rapid clicks read the latest state instead of a stale render-scope value, for both + and − buttons. Confidence: 0.7
