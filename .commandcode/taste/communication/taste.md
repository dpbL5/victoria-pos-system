- When the user floats their own implementation idea framed as "tại sao không X?" / "có cách nào Y không?" (e.g. "why not just query the session by the sessionId the invoice already has instead of running the backfill"), treat it as a proposal to be engineered, not a yes/no question: (1) affirm what is right about the direction first, before any correction; (2) verify the premise against the actual schema/data — their mental model of which rows carry which value is often inverted (the broken rows are precisely the ones missing the id they'd query with), and say so with evidence; (3) improve the mechanism rather than adopting it verbatim — they instinctively reach for an extra client round-trip / new API call, when the same result is normally obtainable server-side inside the existing query (extend the ORM `include`/join plus a read-path fallback), so state plainly that no new API call is needed; (4) surface what the idea still cannot fix (DB-side filters, aggregates and indexes that query the broken column can't be rescued by read-path fallback) and hand back a small labelled option set (keep as-is / add fallback / add fallback and drop the script) with the agent's own inclination, then wait for their pick.
