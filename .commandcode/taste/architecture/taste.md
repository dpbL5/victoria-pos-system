- Prefer a lean data model: avoid creating persistent entity records for transient/anonymous data when a simple field on the existing record suffices. The user explicitly flagged auto-creating an anonymous `Customer` row per walk-in check-in as wasteful ("phí tài nguyên") and confirmed the lightest design — store the guest name directly on `Session` (`customerName`) with `customerId` nullable, only creating a `Customer` when a membership is actually registered. Confidence: 0.9
- Schema restructures must be non-destructive and migration-safe ("không làm hỏng db"): preserve existing data by copying values to the new field, only removing rows provably unreferenced (e.g., anonymous walk-in customers with no membership), and keeping records that back other features intact — never drop or break data that other flows still depend on. Confidence: 0.75
- Retried multi-step flows must not duplicate side effects (explicitly flagged risk: "ấn Gia hạn & check-in nhiều lần tạo ra nhiều customer"): after an earlier step succeeds but a later one fails (e.g., register membership OK, check-in fails), update client state so a retry performs only the failed step instead of re-running the completed mutation and creating duplicate customers/memberships/invoices. Confidence: 0.60
- Avoid duplicating the same business flow across multiple UI surfaces: when a flow (e.g., membership register/renew) already has a dedicated screen, keep that screen as the single entry point and have other surfaces (e.g., the check-in dialog) delegate via navigation rather than re-implementing the logic — duplicated entry points drift and multiply side-effect risk (user resolved the duplicate-customer bug by removing register/renew from the dialog entirely and routing to the membership tab). Confidence: 0.75
- Soft-delete user-facing entities that carry financial/audit history (e.g., members) rather than hard-deleting: add a `deletedAt` column, default-filter it out of `findById`/`findMany` so deleted entities vanish from lists, search, and check-in flows, and expose dedicated `softDelete(id, at)` + `findByIdIncludingDeleted(id)` repository methods so the delete use-case can distinguish "not found" vs "already deleted". Block deletion while the entity has live dependents (e.g., an ACTIVE session) with a 409 error telling the user to resolve it first; never touch financial records (invoices/payments) in the delete path. Confidence: 0.75
- Use-cases that wrap DB writes follow a two-phase structure: pre-transaction guards (validate + authorize, returning typed errors) then an exported `runXxxTx(tx, input)` transaction body; tests call `runXxxTx` directly with fake repositories instead of mocking Prisma's `$transaction`. Confidence: 0.65
- When adding a new transient state to an entity (e.g., pausing a session), prefer a nullable timestamp field (`pausedAt`) and derive the state from it rather than expanding the status enum — this preserves backward compatibility with every existing filter/query on the original status values across the codebase, and avoids cascading changes to reports, list endpoints, and business logic that all filter on `status='ACTIVE'`. Confidence: 0.65
- Route handlers must never cast the `repositories` bundle (`repositories as never`) to satisfy helpers that expect a Prisma store/delegate — the cast hides the mismatch until runtime (e.g., `db.shift.findFirst is not a function` → 500). Use the domain port exposed on the repository (e.g., `repositories.shift.findOpenForStaff(staffId)`) for domain queries, and pass `prisma` from infrastructure explicitly to read helpers that genuinely need Prisma delegates (e.g., `getShiftTransactions(prisma, id)`), consistent with the three-layer boundary. Confidence: 0.6
- In long transactions that both move related rows and decrement counters (e.g., multi-pricing-group checkout: `movePlayersToGroup` + `decrementGroupRemaining`), never derive decrement counts from a stale in-memory context snapshot (e.g., `session.pricingGroups` captured before the moves) — instead decrement per group from the actual selection counts (`playersToBillByGroup[i]`) against the real persisted group ids (write back the created id into the pending assignment object so the decrement loop can use it); this class of bug surfaces as `PRICING_GROUP_UNDERFLOW` ("số người checkout lớn hơn số người còn lại nhóm giá") when the same players are counted against their old group. Confidence: 0.6
