# api
- Audit-log destructive operations (e.g., DELETE endpoints) by writing to the activity journal/log with entity type and relevant field details (via `logActivity`) for traceability. Confidence: 0.75
- Log user-attributed operational actions beyond destructive ones: when capturing state during an open shift (e.g., counting tools), write an ActivityLog entry carrying the acting user's `userId` plus identity details (username/fullName/role) and a timestamp, append-only, rather than overwriting shared state — user explicitly asked to "log lại user sau khi đếm dụng cụ". Confidence: 0.6
- One-shot business constraints (e.g., counting tools only once per shift) must be enforced server-side in the use-case with a dedicated error code (e.g., `TOOL_COUNT_ALREADY`) so the API rejects duplicates even if the UI is bypassed; the client then derives its disabled state from the server-returned data rather than trusting the UI alone. Confidence: 0.7
- When operational data captured at one point (e.g., tool counts at shift open) will be needed later for reconciliation (e.g., match check at shift close), persist it in a structured, queryable field (`ShiftTool.openCount`) rather than only in an append-only activity log — logs are for audit/traceability, the structured field is what the later flow compares against ("lưu lại đâu đó để khi đóng ca lấy đó làm dữ liệu so sánh khớp hay không"). Confidence: 0.65
- Manually extract CSRF tokens from `document.cookie` and set the `X-CSRF-Token` header for mutation requests (PATCH/DELETE) when existing API helpers only support POST. Confidence: 0.70
- Use `requireMutationAuth` for write operations (POST/PATCH/DELETE) and `requireAuth` for read operations; check `auth.role !== 'ADMIN'` for admin-only access rather than relying on a dedicated `requireAdmin` function. Confidence: 0.70
- Use typed API client helpers (`apiJson<T>(url, options)` for responses, `jsonRequest(body)` for building POST/json request options) from `@/features/pos/api` instead of raw `fetch` in client components. Confidence: 0.70
- Sanitize string inputs from request bodies on the backend: `JSON.parse` then trim, type-coerce (`String(...)`), and cap length before passing to business logic. Confidence: 0.65
- Consolidate duplicated client API helpers (e.g., `api.ts`, `api-client.ts`) into a single API client exposing one typed `apiJson<T>()`/`jsonRequest()` contract with a single `getCSRFToken()` implementation, and fix reverse dependencies (e.g., a shared `swr-fetcher` importing from a feature folder) rather than tolerating parallel helper sets. Confidence: 0.85
- Prefer a single error model across the API: return `Result`/`HttpErrorInfo` and let route handlers map uniformly via `resultToResponse`/`apiError`, instead of mixing it with thrown errors that routes catch by string-matching `error.message === 'UNAUTHORIZED'`. Confidence: 0.70
- Reuse server-side Zod validation schemas for client forms (they're isomorphic) rather than letting client and server validation drift into separate definitions. Confidence: 0.60
- When a list/search endpoint can cheaply include derived status fields (e.g., `includeMembershipStatus=true` returning `membershipStatus`/`currentMembership`), prefer enriching the list response over making the client issue an extra per-item status request afterward; keep a fallback fetch when the enriched fields are absent. Confidence: 0.6
- When building query strings with `URLSearchParams`, let the API encode values itself — do not pre-encode with `encodeURIComponent` before `params.set(...)` (URLSearchParams re-encodes the `%`, so the server decodes only one layer and `JSON.parse` of the received value fails). Confidence: 0.6
- For admin-only destructive endpoints, follow the codebase's established route pattern: `requireAdmin()` + `validateCSRF(request)` + `apiError(ERR_FORBIDDEN)` (as in `membership-plans/[id]/route.ts`) — `requireMutationAuth` does not perform role checks, so it is insufficient for admin-only actions. Confidence: 0.6
- Quote/preview endpoints that feed a money-collection screen (e.g., `checkout-preview`) should return the same itemized detail the final invoice will show (e.g., per-player `playerPricing` with hours, subtotal, discount, total, pricing-rule name), computed with the exact same per-player logic as the actual checkout use-case (bill-count slice order, per-player `calculatePlayerPrice`, promotion, pricing-rule name from the group snapshot) — the pre-payment quote and the post-payment invoice must render identical lines so staff see the exact charge before collecting. Confidence: 0.6
- When role-based access splits into two tiers (operational vs system administration — e.g., MANAGER keeps operational rights like reports/CSV export/inventory/close-shift but loses system admin like pricing/promotions/tools/staff/cashflow/students), add a dedicated `isAdminOnly(role)` helper alongside `isManagerOrAdmin(role)`, make `requireAdmin()` mean ADMIN-only, and classify every guarded endpoint/use-case as operational (manager keeps, via `requireAuth`/`requireMutationAuth` + explicit `isManagerOrAdmin` check) vs administrative (admin-only, via `isAdminOnly`) rather than one coarse shared admin check. Confidence: 0.65
- Role-conditional client-side API calls must use the same role predicate as the endpoint's own server guard: a screen that calls an admin-only endpoint (e.g., `/api/users`, guarded by `requireAdminOnly`) when `isManagerOrAdmin(role)` will 403 for MANAGER and take down the entire screen — the whole `/shifts` screen errored because `shifts-screen` gated its `/api/users` fetch on `isManagerOrAdmin`. When a role's access to a module changes, audit every role-conditional fetch in the affected screens and align the predicate with the endpoint's authorization (call admin-only endpoints only under `isAdminOnly`). Relatedly, when restricting a role from a module (e.g., STAFF barred from the shifts list), carve out the operational query subset the role still needs for its own POS workflow (e.g., `current`/`openOperational`) and enforce that carve-out server-side with a 403 for the rest — not just by hiding navigation. Confidence: 0.7
